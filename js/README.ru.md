# anti-detect-browser

[English](README.md) | **Русский**

Дайте своей автоматизации - или своему AI-агенту - настоящий браузер, который веб **не сможет отличить от человека**. Отпечатки настоящих устройств подменяются на уровне ядра, управление идёт через тот же API Playwright, который вы уже пишете.

## Почему anti-detect-browser

### Локальность прежде всего, и бесплатно

Создавайте **неограниченное количество профилей браузера на своей машине - бесплатно, навсегда.** Никакой платы за профиль, никакой платы за место. Каждый профиль - это полностью изолированная личность: собственный отпечаток настоящего устройства, куки, хранилище и прокси, - сохранённая на диске и восстанавливаемая побайтово при следующем запуске. Назовите профиль - и он существует; ничего дополнительно готовить не нужно.

### Готов к работе с агентами из коробки

Поставляется как **MCP-сервер** - одна строка (`npx anti-detect-browser --mcp`) добавляет полностью снабжённый отпечатком браузер в Claude или любой MCP-клиент, так что ваш агент может переходить по страницам, кликать, вводить текст, читать содержимое и делать скриншоты настоящего веба. Предпочитаете код? `launch()` возвращает стандартные Playwright `BrowserContext` и `Page`, поэтому существующие скрипты работают без изменений - меняется только строка запуска.

### Технически впереди

Отпечатки подменяются на **уровне ядра** (собственный рантайм на базе Chromium 149), а не хрупкими патчами на JavaScript, которые антибот-системы вычисляют с первого взгляда. Сигналы остаются **согласованными** между Canvas, WebGL, WebGPU, шрифтами, аудио, `navigator`, экраном и часовым поясом - ничто не противоречит друг другу, потому что это профиль реального устройства, а не рандомизированный шум. Часовой пояс и геолокация **автоматически следуют за прокси**.

### Аутентифицированные прокси - и ничего не нужно устанавливать, чтобы они заработали

Передайте `http://`, `https://` или **`socks5://user:pass@host:port`**, и учётные данные будут обработаны **внутри движка** - запросы `407` для HTTP/HTTPS обрабатываются прямо в сетевом стеке, SOCKS5 - по протоколу согласования логина/пароля из RFC 1929. Вспомогательное расширение не устанавливается, поэтому `chrome://extensions` остаётся пустым; расширение для авторизации прокси, которое до сих пор поставляют многие антидетект-браузеры, можно перечислить с любой страницы, и само по себе является демаскирующим признаком. Учётные данные доходят только до сетевого процесса и никогда - до процесса рендеринга.

## Быстрый старт

```bash
npm install anti-detect-browser
```

Получите API-ключ в панели управления на [antibrow.com](https://antibrow.com/ru), затем:

```ts
import { AntiDetectBrowser } from 'anti-detect-browser'

const ab = new AntiDetectBrowser({ key: process.env.ANTI_DETECT_BROWSER_KEY })

// Unlimited local profiles - just name one. It's created on disk on first use.
const { page, browser } = await ab.launch({ profile: 'shopper-01' })

await page.goto('https://whoer.net')      // standard Playwright from here on
console.log(await page.title())
await browser.close()
```

С управляемым резидентским прокси (часовой пояс и гео следуют за ним) и визуальной меткой:

```ts
const { page } = await ab.launch({
  profile: 'shopper-02',
  proxyId: 'px_xxxxxxxx',   // managed residential proxy - activated + injected for you
  label: 'acct@shop.com',   // drawn by the kernel in front of the address bar
})
```

`launch()` возвращает `{ browser, context, page, profileDir }` - `context` и `page` являются настоящими объектами Playwright.

## Android-профили

Попросите телефон - и профиль им станет, на той же машине с Windows, macOS или Linux, на которой вы уже работаете:

```ts
const { page } = await ab.launch({
  profile: 'phone-01',
  deviceType: 'android',   // 'desktop' (default) | 'android'
})
```

Это **симуляция, запущенная на настольной машине**, а не парк устройств и не удалённый телефон. Меняется личность, которую видит страница, - и всё это отвечается прямо в ядре:

| Поверхность | Что сообщает Android-профиль |
|---|---|
| UA + client hints | UA `Mobile Safari`, `Sec-CH-UA-Mobile: ?1`, `Sec-CH-UA-Platform: "Android"`, настоящие `model` и `platformVersion`, `formFactors: ["Mobile"]`, пустые `architecture` / `bitness` |
| `navigator` | `platform: "Linux armv81"`, `maxTouchPoints`, мобильные значения ядер/памяти, отсутствие плагинов и mime-типов, `pdfViewerEnabled: false` |
| Сенсор и раскладка | `ontouchstart`, `window.orientation`, портретная `screen.orientation`, `(pointer: coarse)` / `(hover: none)`, окно подогнано под размер экрана устройства, так что `innerWidth === screen.width` на странице с viewport-meta |
| GPU | мобильные unmasked vendor/renderer и расширения сжатых текстур ETC/ASTC, которые действительно выставляет GPU телефона |
| Экран, аудио, шрифты, соединение | взяты с того же устройства, что и всё остальное |

Три настоящих телефона поставляются **прямо внутри пакета**, поэтому профиль на бесплатном тарифе может быть Android без единого сетевого запроса. Каждое поле берётся с одного устройства - пакет выбирает целую строку, а не отдельное поле, потому что только так значения согласуются между собой.

Важно знать две вещи:

- **Тип устройства фиксируется при создании.** Он хранится в персоне профиля, поэтому передача `deviceType` для уже существующего профиля ничего не даёт. Чтобы переключиться, создайте новый профиль.
- **Для Android нужно ядро `151` или новее** - первое, которое несёт поддержку мобильных устройств. Для нового Android-профиля SDK берёт самое свежее подходящее ядро, устанавливает его за вас и завершается явной ошибкой, а не запускает настольное ядро под маской телефона. Проверить версию самостоятельно можно через `kernelSupportsAndroid(version)`, а получить список подходящих - через `androidCapableKernels()`.

Хотите, чтобы личность бралась из библиотеки отпечатков на сервере, а не из встроенной таблицы - каждый раз другая реальная машина, Android или Windows?

```ts
await ab.launch({ profile: 'phone-02', deviceType: 'android', realFingerprint: true })
```

`realFingerprint` доступен на платных тарифах; бесплатные ключи сервер отклоняет, а не тихо понижает до сгенерированной персоны. Как и `deviceType`, применяется только при первом создании профиля.

## Поддержание ядра браузера в актуальном состоянии

Ядро браузера с отпечатками со временем получает новые сборки (свежие мажорные версии Chrome, исправления маскировки). Установленные ядра кешируются и **никогда не подменяются без вашего ведома** - вы сами решаете, когда обновляться.

```ts
// Any installed kernel have a newer build published?
if (await ab.hasKernelUpdate()) {
  const updated = await ab.updateKernel()   // pull the newer build(s)
  console.log('updated kernels:', updated)  // → ['150']
}

// Or inspect per-version detail
const status = await ab.checkKernelUpdates()
// [{ version, label, installed, installedBuild, availableBuild, updateAvailable }]

// Update just one version, with progress
await ab.updateKernel('150', msg => console.log(msg))
```

Даже без этого `launch()` тихо проверяет (один раз за процесс, в фоне) и выводит однострочное уведомление, если доступна более новая сборка ядра, - так вы будете в курсе, но обновление никогда не произойдёт у вас за спиной и не замедлит запуск:

```
[anti-detect-browser] A newer browser kernel build is available for: Chrome 150. Run browser.updateKernel() to update now, or launch with { updateKernelBeforeLaunch: true }.
```

Хотите, чтобы всё происходило само? Позвольте `launch()` проверить **и обновить** ядро профиля перед стартом - **по умолчанию выключено**:

```ts
await ab.launch({
  profile: 'shopper-01',
  updateKernelBeforeLaunch: true,   // default false - when true, updates then launches (no notice)
})
```

Если машина офлайн, проверка молча пропускается, и браузер запускается с уже установленным ядром - обновления никогда не блокируют запуск. (Уведомление идёт в stdout; MCP-сервер направляет его в stderr, чтобы не засорять канал JSON-RPC.)

## Использование из AI-агента (MCP)

Добавьте это в конфигурацию своего MCP-клиента - и агент получит скрытный браузер:

```json
{
  "mcpServers": {
    "anti-detect-browser": {
      "command": "npx",
      "args": ["anti-detect-browser", "--mcp"],
      "env": { "ANTI_DETECT_BROWSER_KEY": "your-api-key" }
    }
  }
}
```

**Инструменты:** `launch_browser`, `navigate`, `click`, `fill`, `screenshot`, `evaluate`, `get_content`, `list_profiles`, `create_profile`, `list_proxies`, `claim_proxy`, `start_live_view` и другие.

`launch_browser` и `create_profile` принимают и `deviceType` (`"desktop"` / `"android"`), и `realFingerprint`, поэтому агент может запросить профиль телефона тем же вызовом, которым его запускает.

## Автоматизация в больших масштабах

Автоматизация обычно создаёт отдельный профиль под каждую задачу. Передайте `temporary: true`,
чтобы такие профили оказывались в отдельном дереве каталогов, не мешая
профилям, которыми вы управляете вручную:

```js
import { AntiDetectBrowser } from 'anti-detect-browser'

const ab = new AntiDetectBrowser({ key: process.env.ANTI_DETECT_BROWSER_KEY, temporary: true })

for (const task of tasks) {
  const { page, browser } = await ab.launch({ profile: `task-${task.id}` })
  await page.goto(task.url)
  await browser.close()
}

// Temporary profiles are never deleted for you.
const removed = ab.clearTemporaryProfiles({ olderThanDays: 7 })
console.log(`removed ${removed.length} temporary profiles`)
```

Три вещи, которые стоит знать:

- **Они не отображаются в десктопном приложении.** Десктопное приложение
  читает только управляемое дерево, поэтому временный профиль для него невидим.
- **Два дерева - это разные пространства имён.** Временный `gmail` и
  управляемый `gmail` - это два разных профиля со своей личностью и куками.
- **Ничего не удаляется автоматически.** Временный профиль хранит свою
  личность и свои сессии столько, сколько вы оставляете его на диске, - это и
  делает его пригодным для повторного использования. Удаляйте их сами через
  `ab.clearTemporaryProfiles()` или
  `npx anti-detect-browser --clear-temp --older-than=7`.

При каждом запуске `temporary: false` возвращает один профиль обратно в управляемое дерево.

### Чтобы окно не мешало вашей работе

Запуск забирает фокус, что становится проблемой, когда автоматизация должна
работать рядом с вашей собственной. `focusWindow: false` открывает браузер
позади того, что сейчас на переднем плане:

```js
await ab.launch({ profile: 'task-01', focusWindow: false })
```

Окно всё ещё на месте и обычного размера - это не headless-режим, поэтому в
отпечатке ничего не меняется; окно просто не выходит на передний план. Порядок
окон определяется ядром, а не SDK, поэтому перед тем, как на это полагаться,
установите для профиля последнюю версию ядра.

### Облачная синхронизация

Запуск сам по себе никогда не создаёт облачный профиль. По умолчанию профиль
синхронизируется только тогда, когда сервер уже знает это имя, поэтому запуск
автоматизации не может заполнить вашу квоту синхронизации профилями, которые
вы вовсе не собирались оставлять. Чтобы поместить новый профиль в облако,
запросите это явно:

```js
await ab.launch({ profile: 'main-account', sync: true })   // create + sync
await ab.launch({ profile: 'main-account', sync: false })  // stay local
```

`sync: true` и `temporary: true` взаимно исключают друг друга; передача обоих
приводит к исключению. `sync: true` также вызывает исключение, если ваш
тариф не включает облачную синхронизацию.

## Что вы получаете

| Возможность | |
|---|---|
| **Отпечатки настоящих устройств** | Подмена на уровне ядра, согласованная между Canvas / WebGL / WebGPU / шрифтами / аудио / часовым поясом |
| **Android-профили** | `deviceType: 'android'` превращает профиль в личность настоящего телефона - сенсор, мобильные client hints, мобильный GPU - на вашей настольной машине |
| **Неограниченные локальные профили** | Бесплатно на любом тарифе - изолированные, устойчивые, без платы за профиль |
| **Стандартный API Playwright** | `launch()` возвращает настоящие `BrowserContext` / `Page` - учить нечего |
| **Самообновляющееся ядро** | Обнаруживает новые сборки ядра браузера и подтягивает их по запросу, либо проверяет и обновляет перед запуском |
| **Встроенный MCP-сервер** | Управляйте им из Claude или любого MCP-агента без клеевого кода |
| **Управляемые резидентские прокси** | Один `proxyId` - исходящий IP, часовой пояс и гео согласованы между собой |
| **Аутентифицированные HTTP/SOCKS5** | Учётные данные обрабатываются в движке (`407` / RFC 1929) - никакого расширения для авторизации прокси, которое можно перечислить |

| **Облачная синхронизация профилей** | Переносите профиль (личность + состояние) между машинами |
| **Параллелизм по тарифу** | Ограничение на одновременные браузеры, применяемое ядром |

Управляемые прокси, Live View и облачная синхронизация доступны на платных тарифах. Локальные профили и полноценный движок отпечатков бесплатны.
